## 6A — Understand each workflow step

Create .github/workflows/tests.yml, preserving indentation:

<!-- reference: learn/06-ci:.github/workflows/tests.yml -->
```yaml
name: Calculator tests
on: [push, pull_request, workflow_dispatch]
permissions:
  contents: read
jobs:
  tests:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    strategy:
      matrix:
        python-version: ['3.11', '3.12', '3.13', '3.14']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: python -m pip install -r requirements.txt
      - run: python -m pytest
```

| Section | Meaning here |
| --- | --- |
| on | Respond to pushes, pull requests, or a manual workflow request |
| permissions | Job gets read access to repository contents |
| runs-on | Use a fresh Ubuntu runner |
| timeout-minutes | Bound the job's duration |
| strategy.matrix | Repeat the job on Python 3.11, 3.12, 3.13, 3.14 |
| checkout | Obtain the committed source |
| setup-python | Select Python; pip caching speeds downloads but does not install requirements |
| pip install | Install the declared dependencies |
| pytest | Run the application's behavior checks |

`${{ matrix.python-version }}` chooses the matrix entry for that job. YAML indentation expresses nesting. Your local .venv is ignored and not uploaded; the runner must install its own packages.

The tutorial's workflow is pass/fail. The practice repository's different workflow runs a points-based grader. Do not confuse a green tutorial check with a numeric exam score.

## 6B — Publish your solution, not the instructor's reference

Run `python -m pytest` locally first. Create an empty GitHub repository under your own account using GitHub's interface. From your statistics-solution folder:

```bash
git status
git add .github/workflows/tests.yml README.md calculator tests requirements.txt pytest.ini values.csv
git commit -m "Automate statistics checks and explain design"
git remote -v
```

If there is no origin, add your new repository, replacing the placeholders:

```bash
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
git push -u origin main
```

If origin already points to your solution, skip adding it and push. If it points somewhere unexpected, stop and inspect before publishing. Do not push your work into the instructor reference or commit .venv.

Authentication is part of GitHub access, not calculator behavior. If a push fails, use your course GitHub setup instructions. Do not paste a token into source or a learning log.

## 6C — Read the run as evidence

Open your repository's Actions tab, choose Calculator tests, and open the run for your latest commit. Expect four Python-version jobs. Inspect the failed step if any job is red.

This is an illustrative failure, not a claim that the reference workflow is failing:

```text
FAILED tests/test_statistics.py::test_known_sample
E assert 14.142135623730951 == 15.811388300841896 ± 1.6e-05
Process completed with exit code 1.
```

| Evidence | Interpretation | Next action |
| --- | --- | --- |
| Assertion from a named calculation test | Dependencies installed and test code ran | Recheck inputs and the required statistical policy |
| 14.1421 instead of 15.8114 | Likely population/sample mismatch | Inspect ddof before changing expectations |
| Exit code 1 | Consequence of unsuccessful tests | Fix the actual cause and rerun |

An installation failure occurs before pytest. A ModuleNotFoundError may indicate missing dependencies or missing committed files. Ubuntu paths are case-sensitive; a differently capitalized filename can behave differently from your local setup.

Run the focused failing test locally, then the full suite. Push a new commit and check that commit's run. An old green run does not verify your latest code.

**Technical checkpoint:** local tests pass and all four jobs for your submitted commit are green. Now explain what the checks establish—and their limits.

## 6D — Reproduce installation from a fresh clone

Clone your own solution into a different folder and create a new environment using [setup](../setup.md). Install requirements, run the application, and run the tests. Do not copy your old .venv. Improve any instruction that assumed a file or package you forgot to commit.

Write your README for someone who has never seen this chat. Include environment steps, running from the root, the fixed CSV contract, sample deviation, errors, testing, and the roles of Command and Simple Factory.

## 6E — Use the vocabulary to explain and transfer

Read [Refactoring.Guru: Why learn patterns?](https://refactoring.guru/design-patterns/why-learn-patterns). Then revisit [pattern categories and features](../patterns-and-features.md) and [language transfer](../language-transfer.md).

Write a short reflection:

1. Which object stores a request, and who decides when it executes?
2. Where does concrete construction occur, and why is it Simple Factory?
3. What would change for a third input source? Include registration, prompts, and tests.
4. Why does the shared statistical function make policy changes easier?
5. When would direct function calls be a better choice?
6. Pick another language: what design relationships transfer, and what language-specific facts must you learn?

No new pattern implementation is required for this reflection.
